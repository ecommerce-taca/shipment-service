# Shipment — unresolved decisions and explicit assumptions

| Priority | Item | Current implementation assumption | Required before |
|---|---|---|---|
| P0 | Shipment create integration decision | The documented Order-Commerce direction is REST `POST /api/v1/internal/shipments`, followed by Shipment lifecycle events. The opt-in `shipment.commands.v1` create consumer remains a separate unapproved Shipment proposal and is not the selected integration path. | Order-Commerce owner must confirm REST request/response/event mapping, auth, retry/reconciliation, and Order state transitions; decide separately whether to keep the optional Kafka create proposal disabled. |
| P0 | Shop Order uniqueness invariant | Kafka maps `shop_order_id` to the existing Shipment `order_id`, but the database currently enforces uniqueness on `(order_id, shop_id)`, not `order_id` alone. | Order-Commerce confirms whether `shop_order_id` always has exactly one immutable `shop_id`; if not, approve a migration and compatible uniqueness/read-path change before Kafka production cutover. |
| P0 | Creation-result event keying | `shipment.created`/`shipment.creation_pending` are keyed by shipment ID; `shipment.creation_failed` has no shipment row and is keyed by command ID. | Order-Commerce/platform confirms this partition-key exception and projection/deduplication rules for command-scoped failures. |
| P0 | Internal service authentication | `X-Internal-Service-Token` configured via env; constant-time compare. | Integration with Gateway/Order; replace with shared token/mTLS mechanism if required. |
| P0 | Quote API mismatch | Use POST with snapshots/items; Order owns the seller-facing GET façade and passes context to Shipment. | Order-Commerce contract update and end-to-end integration. |
| P0 | Buyer email for Notification | `buyer_email` is required in create request because delivered/failed events require an email recipient. | Notification email integration; docs currently say recipient is required. |
| P0 | GHN sandbox API | Adapter deliberately fails closed; actual create/quote/cancel/lookup API not implemented until verified carrier contract and credentials exist. | Any GHN sandbox integration test. |
| P1 | Checkout and carrier fee reconciliation | Shipment request input remains `shipping_fee`; explicit output is `checkout_shipping_fee`, with separate nullable carrier quote/actual values and derived delta. Order-Commerce is not implemented here; consumers must use the explicit checkout field, not deprecated `shipping_fee`. | Order-Commerce owner confirms field mapping and customer-facing delta/settlement policy. Shipment cannot record actual carrier charge without authoritative carrier data. |
| P0 | Webhook auth | Generic HMAC-SHA256 header signature + exact source-IP allowlist for local contract tests only. | Carrier sandbox / production. Must replace with carrier's actual documented mechanism. |
| P1 | SPX/J&T adapters | Not implemented; quote returns unavailable. | Seller can successfully choose these carriers. |
| P1 | Kafka consumer DLQ policy | Listener uses bounded retries and a configurable DLT; DB worker exhaustion is parked in `shipment_command_dlq` and replay requires an operator endpoint. Topic name, retention, ACLs, alerting and operational ownership are configured provisionally. | Platform owner confirms topic provisioning/retention/ACL; Ops/Security confirms DLT monitoring and replay authorization/retention. |
| P1 | Creation result events | `shipment.creation_failed` and `shipment.creation_pending` are implemented as proposed event types; existing event consumers may not understand them. `shipment.failed` remains delivery failure only. | Order-Commerce and Notification/platform confirm result event schema and projection behavior before enabling producer/consumer in integrated environments. |
| P1 | Order cancellation race | A durable tombstone and leased cancellation worker now prevent early `order.cancelled` from being silently lost before create; cancellation during reconciliation waits. Operator-review state is replayable with privileged endpoint. Carrier/order policy for a cancellation after pickup remains an integration decision. | Order-Commerce confirms `order_id` identifies the Shop Order and the desired outcome after carrier pickup; Ops confirms replay path. |
| P1 | Carrier idempotency/reconciliation | Adapter gets an idempotency key; create timeout, HTTP 408/409/425/429 and 5xx are treated as ambiguous and kept in reconciliation; job only recovers when `findByIdempotencyKey` returns positive evidence. | Carrier owner confirms response classification, idempotency and authoritative positive/negative lookup semantics; GHN implementation must use that contract. |
| P1 | Carrier creation result fields | `CarrierCreateResult` currently requires nonblank external shipment ID and tracking code within persisted column limits; incomplete adapter responses fail closed into reconciliation. | Carrier owner confirms whether tracking code is always available at create time; if not, agree which identifier establishes `shipment.created` and how later tracking-code updates are published. |
| P1 | Carrier cancellation ambiguity | Cancellation calls the adapter before committing Shipment status/idempotency result. If the carrier accepts cancellation but the database commit fails, safe replay depends on carrier honoring the same idempotency key; cancellation lookup/reconciliation is not implemented. | Carrier owner confirms cancellation idempotency and authoritative lookup/cancel-result behavior; implement recovery before production GHN cancellation. |
| P1 | Kafka inbox PII retention and operations access | Original command/cancellation envelopes are stored for durable retry/DLQ and may contain buyer/address data. DB-backed replay requires a separate operator token and trusted operator role headers. | Security/Data/Ops approve DB access, at-rest protection, retention/purge and trusted ingress/token rotation. |
| P1 | Shared Kafka metadata | Outgoing event envelope carries optional correlation/causation; `OutboxPublisher` does not yet propagate agreed W3C trace/request IDs as Kafka headers. | Platform Kafka convention owner confirms required headers and propagation; implement only to the agreed header contract. |
| P1 | Kafka record size | Shipment create commands and relevant `order.cancelled` events are capped at 256 KiB UTF-8 in the consumers; this is a local defensive limit, not yet a shared contract. | Platform aligns producer, broker, topic and consumer max-record settings or confirms a different agreed limit. |
| P1 | Strict event ordering | Outbox prevents a row later by application `created_at`/ID ordering from overtaking an earlier pending row, but it has no monotonic per-aggregate sequence and app clocks may skew. | Order-Commerce/platform confirms whether per-key Kafka append order is sufficient or strict aggregate sequence/gap handling is required; if strict, add a DB-owned sequence contract and migration. |
| P1 | COD eligibility | Create request carries `payment_method`; positive COD requires `COD`. | Order must send the field consistently. |
| P2 | Structured JSON logging | Current code avoids sensitive fields in explicit logs, but the exact shared JSON log schema/trace enrichment is not fully wired. | Observability integration. |
| P2 | Schema rollout | Single initial Flyway migration consolidates DB spec tables. | If team requires staged migrations, split before baseline release. |
| P2 | Readiness | Checks database and Kafka topic configuration but does not currently prove broker reachability. | Production probes. |
| P2 | Return/exchange and multi-package | Out of scope for v1. | Product/finance decision. |

## Not assumed

- No real GHN tracking code or fee is fabricated.
- No SPX/J&T availability is claimed without adapters.
- No direct database access to Order/Auth User is added.
- Shipment never initiates refund/payment capture.
- A carrier timeout is not treated as a definite failure or success without reconciliation.
